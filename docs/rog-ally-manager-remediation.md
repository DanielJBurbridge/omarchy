# SteamOS Manager power-only feasibility and remediation

Status: bounded design and an **unbuilt prerequisite patch**, not a deployable backend. Stock `steamos-manager 26.4.1-3` remains **NO-INSTALL**, including inactive installation. No package, signature, firmware capability, server authorisation, full rollback or hardware acceptance is established here. Frozen integration `47e0e976f47c86edf9962d0debde9b571fadc385` and its live rollout are unchanged.

The next bounded [session authority decision and private-bus denial proof](rog-ally-power-authority.md) keeps production grants denied: the target supervisor has no verified logind binding, and normal desktop login bypasses it. Root-relayed current-performance firmware-path readability is recorded there without implying verified units, outside-profile capture or any authority/takeover acceptance.

## Decision and immutable evidence

Keep Manager as a reuse candidate, but require a separate power-only build/API before takeover. Removing install payload or changing a D-Bus allow rule cannot repair the current root authority and incomplete state contract. This increment deliberately does not produce a PKGBUILD that appears installable. `omarchy-steamos-manager-power` is a reserved name, with **no accepted identity, version or artifact**.

## Reachable code and the required cuts

Upstream currently exposes no existing power-only mode: root/user service config is empty for these duties, root interface registration is monolithic, and removing platform configuration alone does not remove root methods. The smallest defensible final boundary is a distinct power-only entry point or mutually exclusive build feature that registers only the reviewed power surface, reusing `hardware.rs` and the RC71L firmware-attribute implementation. The existing complete Manager build must keep its defaults. A root/user pair cannot mix full and power-only modes; use a build identity/capability handshake and refuse a mismatch.

Initial scope should be platform profiles plus all three PPT limits. Fan curves, SMT, thermal limits, networking, input, storage, firmware and login policy remain absent. Keeping the experimental client code does not make its other controls accepted. Legacy Steam `PerformanceProfile1`/`TdpLimit1` adapters, if retained for QAM compatibility, must forward to the same authorised transaction engine; there must be no old root setter bypass. Their actual QAM compatibility is still unverified.

## Separable prerequisite supplied here

[0001-input-management-opt-out.patch](../plans/rog-ally-manager/0001-input-management-opt-out.patch) applies to the pinned pristine source, without the unrelated CachyOS patches. It adds root-owned configuration:

```toml
[services]
manage_input = false
```

The candidate skips both DeckService and DS inhibitor startup and ignores later inhibitor commands before state or hardware changes. Default behaviour remains enabled for existing upstream users. Runtime reload keeps the current value and logs that a restart is required. It does not introduce a reload-triggered service shutdown. Existing queued D-Bus setter acknowledgement remains unchanged: an ignored inhibitor command is logged by RootContext, rather than returned synchronously to the caller. The final power-only variant must remove this interface entirely.

The patch retains upstream MIT notices; [UPSTREAM-LICENSE](../plans/rog-ally-manager/UPSTREAM-LICENSE) accompanies it. The included Rust test exercises real Serde defaults/explicit configuration, but has **not been compiled or run**. Application/checksum checks are not a Rust build or proof of startup/hotplug behaviour. This patch does not disable Wi-Fi, session duties, broad root authority, tracing, or incomplete PPT handling. It is neither a security fix nor deployment clearance and must not be installed alone to obtain power controls.

`python3 plans/rog-ally-manager/verify-prerequisite.py /path/to/pristine/pinned/source` checks the recorded source/lockfile hashes, patch/licence hashes and zero-fuzz application in a temporary fixture. It does not modify the supplied tree, fetch sources or run Cargo. The result is deliberately labelled with those limits. A changed-source fixture is rejected before patching. The snapshot schema has been parsed as JSON; no formal JSON Schema validator or Rust build is installed/run for this increment.

## Server authority required before packaging

The root service must enforce all of the following on **every** mutation, including legacy property adapters, apply, restore and resume reapplication:

1. Resolve the actual system-bus message sender through D-Bus credentials. Never trust a UID, PID, session string or `SerialOrderValidator` supplied as an argument. A session proxy is not trusted merely because it has the right well-known name.
2. Use logind to verify an active, local graphical owner on the intended seat, and recheck that ownership at execution. A user daemon launched by the user systemd manager may not belong to the requesting login session; do not guess a session from the PID or silently treat every process of an active UID as that session. If delegation is needed, it requires a separately specified root-issued, expiring, sender/session-bound grant and tests; no such mechanism is implemented here.
3. Use a dedicated narrow Polkit action for the profile/PPT transaction, with inactive/remote denial and an explicit initial policy such as active-local `auth_admin_keep`, rather than an all-yes rule. Use a system-bus-name subject resolved from the actual caller, not a client-supplied Unix-process identity. Deny unavailable authorisation services, cancellation and stale credentials. Prompt/caching behaviour and delegation to the policy listener need an agreed interaction design before controller usability can be claimed. Do not install a permissive fallback to hide that gap.
4. Independently verify exact ASUS/RC71L device selection, supported firmware attributes, current power source, per-field hardware bounds and the reviewed RC71L software safety policy. Disable forced device-config overrides in the restricted entry point. Root must own and validate the bounds; client checks alone cannot stop a direct caller writing larger values.
5. Serialise captures and mutations under one root transaction lock, reject stale epochs and overlapping writers, and invalidate grants/snapshots on logout, owner change, boot, backend replacement or device removal. Reject unknown interfaces/attributes; accept no arbitrary sysfs path, helper command, service or configuration filename from a caller.

A narrower D-Bus policy can restrict transport after the interface split; it does not replace server authorisation. Do not patch the current broad policy with a user/group allow rule and call the complete daemon safe. No proposed authorisation code or Polkit policy is shipped by this increment. The UID/session delegation question is a specific upstream/API design blocker, not permission to guess an active session.

## Proposed typed profile/PPT contract

[snapshot-v1.schema.json](../plans/rog-ally-manager/snapshot-v1.schema.json) is a design schema, **not an implemented API**. Version 1 covers exactly the profile and all three limits touched by the first restricted variant. It includes backend build identity, boot/device generation, owner UID/session/seat, mutation/source epochs, root policy identity, current profile/choices, and separate unsigned-watt current/min/max/step readings for SPL, SPPT and FPPT. A zero or absent value must not stand in for a failed read. Semantic validation additionally requires ordered ranges, representable steps, current profile in choices and a complete device-specific safety policy.

| Proposed operation | Typed request | Result and guarantee |
| --- | --- | --- |
| `CaptureProfilePpt1` | No paths/UIDs; identity comes from the authorised sender | Complete `SnapshotV1` plus an opaque 128-bit ID. Root retains the authoritative snapshot bound to that caller/session/build/boot; a client-edited JSON object is not a restore authority. No writes, including no temporary switch to performance to make capture possible. |
| `ApplySustained1` | Snapshot ID (`16 bytes`), expected mutation/source epochs (`u64` each), requested profile (`string` from choices), sustained watts (`u32`) | A transaction result with before/after observations of profile **and SPL/SPPT/FPPT**, per-field write outcomes, current epochs and completion status. SPPT/FPPT derive from documented backend policy and each firmware minimum, subject to separately approved burst caps. Existing SPL25/30 W ceilings do not define safe burst caps; missing reviewed burst caps blocks writes. |
| `RestoreProfilePpt1` | Root-held snapshot ID and expected epochs | Restore original profile and **each original** SPL/SPPT/FPPT value, not values recomputed from SPL. For example, restoring a captured 30/43/53 W tuple must not claim success after setting 30/30/30 W. Reject a snapshot whose tuple violates current source/capability policy. |

The proposed `TransactionResultV1` has a transaction ID (`16 bytes`), status enum `applied | rolled_back | partial | restore_pending | source_changed | interrupted`, before snapshot ID, after observation, current mutation/source epochs (`u64`), and ordered field outcomes. A field outcome names exactly `profile | spl | sppt | fppt`, stage `validate | apply | verify | rollback`, state `not_attempted | written | verified | failed | unreadable`, and a fixed error code. After observation contains profile and each PPT value as a tagged `readable(value) | unreadable(error_code)` union; partial/unreadable values are never a complete SnapshotV1. `applied` and `rolled_back` require every affected field to be readable and equal to the intended tuple. Errors include `NotAuthorised`, `UnsupportedDevice`, `IncompleteCapture`, `UnsafeRange`, `StaleSnapshot`, `OwnerChanged`, `SourceChanged`, `WriteFailed`, `ReadbackMismatch`, `Timeout` and `RollbackIncomplete`; no optimistic success on queued acknowledgement.

Required transaction semantics:

- Capture all originals and all three ranges before the first write. Current Manager's performance-only `TdpLimit1` registration cannot supply this in quiet/balanced mode. The backend needs a read-only all-attribute capture independent of public profile gating; if hardware cannot read it without changing mode, return `IncompleteCapture` and perform no writes.
- Validate the entire intended tuple, actual source epoch and authority first. Use reviewed dependency/order rules, reducing limits before increasing them where the driver permits. Changing profile can reset firmware values: capture before the profile change, then read all fields again and apply the intended tuple. Never assume profile changes leave burst values intact.
- Treat sysfs as non-atomic. A failure after any field write triggers best-effort restoration of **all possibly affected fields**, with independent readback. Record each attempted write and its completion. A failed/uncertain write can have changed hardware; do not restore only fields whose syscall returned success.
- A client timeout/disconnect is an unknown transaction outcome, not cancellation or success. Root owns completion/rollback and exposes `GetTransaction1(id)` plus a completion signal; retries use an idempotency key and do not start a second mutation. A synchronous response must wait for verified completion. Root termination/crash requires a root-owned pre-write recovery journal and an explicit recovery procedure; no guarantee across power loss is inferred from a user-side `finally` block.
- Observe UPower/logind events without polling. A source change invalidates the epoch and causes revalidation between writes and after readback. An AC snapshot above battery caps must not be blindly restored on battery. Move only to an independently reviewed battery-safe tuple, or report `restore_pending`/`partial` with actual observations and required recovery (for example reconnect AC). Do not weaken limits to make rollback appear complete. Physical source change and multiple firmware writes cannot be made atomic; report that limitation.
- On resume, invalidate cached hardware observations and recapture capabilities/source before applying preferences through this same engine. Never replay a pre-resume snapshot as though its epoch were current. The existing Omarchy listener remains the only AC/DC/resume policy owner; the restricted backend owns execution, bounds and transaction completion, not a competing profile daemon.

Extending beyond this scope needs typed complete footprints: all affected CPU governor policies rather than CPU0; GPU mode plus both SCLK endpoints rather than one frequency; explicit boost/charge/default state and verified queued completion. Until then those controls must report unavailable in the restricted variant. No full rollback is promised by the current experimental Python client or legacy setup receipt.

## Future package and takeover boundary

The final package needs a distinct approved identity/version and build-capability identity, not a renamed copy of the same binary. Use the pinned upstream commit/archive, individually hashed patch series and licence, unchanged or explicitly reviewed Cargo.lock, checksummed vendored crate/git sources, a pinned compiler/build-root closure and `cargo build --frozen --offline`. Do not let `make build` fetch dependencies, accept moving tags, or regenerate a lockfile silently. Re-resolve runtime/build closures after the actual feature cuts; the original closures are not the restricted package's closure. No full Rust build is authorised by this design increment.

Package only the restricted binary, minimal RC71L data/interface definitions, minimal root/user units and their explicit authorisation policy. Use an explicit allowlist manifest. No package scriptlet, pacman hook, preset, D-Bus auto-activation service file, user auto-start, cleanup service, SDDM drop-in, PlasmaLogin marker, Orca/CEC configuration unit, broad platform helper configuration or networking Polkit helper. Installing or removing the artifact must not enable/start/stop services or write login/network configuration. Later actual artifact review must inspect both payload and `.INSTALL`/hook behaviour; a hand-written expected manifest is not evidence of the produced artifact.

Before installation, the sole rollout owner must record package versions/hashes, active/enabled/masked and activation state of every relevant system/user owner, existing receipts and original complete root power snapshot where possible. The reviewed package must have no activation so that receipt remains a true pre-takeover baseline. If an earlier package was installed and auto-enabled services without a pre-install receipt, classify ownership provenance as unknown; do not reconstruct it from post-install state. A fresh, explicit recovery decision is required.

Only after artifact/signature/manifest/dependency review and isolated hostile-caller/partial-write tests may setup be changed to expect the approved identity **and** capability/build contract. Setup must not be unlocked merely by changing a package-version string. Preserve legacy rollback for any existing receipt, clearly stating its SPL-only/pre-install limitations. Then the sole rollout owner can probe actual RC71L attributes and perform staged install/write/restore/AC/DC/resume/controller/touch/QAM acceptance. No such probe, installation or acceptance occurs here.

## Small next steps and exact remaining blockers

1. Review the input opt-out prerequisite independently; run its Rust config/startup/hotplug tests later in an agreed isolated build. It may be proposed upstream only after explicit authorisation to contact maintainers.
2. Agree the minimal power-only entry point and caller/delegation policy. Implement and test absent non-power methods/side effects plus denied inactive/remote/spoofed callers before considering dependency removal.
3. Implement the all-three-PPT transaction engine/API and failure-injected tests (each write/read fails in turn; timeout/disconnect; source change; resume; daemon termination/recovery). Establish whether the device can supply a complete read-only baseline outside performance mode and review actual burst caps.
4. Review a locked build and actual package artifact, pre-install receipt and restricted setup expectation; only then consider physical rollout.

The unavoidable blockers are missing upstream power-only and authorisation/delegation boundaries, missing complete PPT transaction/restore API, unaccepted artifact/dependency closure and unprobed firmware capabilities. A narrow input opt-out, typed design or source test cannot clear them. This finite increment prepares the separable work; integration/root choose the next bounded implementation step.
