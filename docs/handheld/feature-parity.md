# ROG Ally feature parity

18 November 2026 AWST. Target the original **RC71L** first. The physical unit is a Z1 Extreme. The same acceptance checks still need a Z1 run before claiming both variants. Ally X, Xbox Ally and other handhelds need their own hardware results.

Parity means a usable handheld on Omarchy: boot, play, suspend and return to a controller-friendly Hyprland desktop. Bazzite and CachyOS Handheld set the reference for the experience. The [prior-art audit](research/parity-gaps-ranked.md) records their implementations and licences. [Bazzite ASUS handhelds](https://docs.bazzite.gg/Handheld_and_HTPC_edition/Handheld_Wiki/ASUS_ROG_Ally/) · [CachyOS Handheld](https://wiki.cachyos.org/installation/installation_handheld/)

The Ally runs runtime and settings `4.0.0.202611180456.r8132.handheld.b7298bc1-1` and gaming-session `1.0.0-11`, on kernel `7.2.15-2-omarchy` and InputPlumber `0.84.0-1`. The 18 November transaction verified all three archives and EFI file digests and created root snapshot #14. The TDP source watcher is active and the resume service is enabled. Earlier candidate `71d6b055` is available with verified digests at `~/omarchy-handheld-pkgs/candidate-71d6b055.XKr0Ks` for rollback. Its clean graphical relogin and physical controller, audio and keyboard tests preceded this upgrade.

**Source** means code in this branch. **Fixture** means an automated test of that path. **Older hardware** means an earlier build or desktop-only path was observed. **Gap** means the feature is absent, incomplete or blocked. Close each row against the exact candidate package versions.

### Installer comparison

The candidate combined Quattro `c6be7abb9` and draft head `515d61405` at merge `89ea3e2cb`. Stock Quattro and both candidate suites exited 1. All three reproduced the browser launch, Mozc browser launch, style submenu, notification content and default Chromium assertions. The three remaining assertions were then probed on candidate and reverted clones sharing package inventories and VM geometry.

| Layout map shows its keys | Original stock stopped at shell IPC. The focused reverted clones reproduced the OCR timeout. | Focused OCR timed out while the hint was visible | Same timeout; per-output OCR read the hint in all four focused captures |

Twelve installed package versions differed between the original RC71L guests because the mirror advanced. The matched clones controlled that difference. The exact late recovery-menu timeout remains unresolved, with a similar wrong-output state on reverted code and a candidate pass on identical inputs. The cloned runs test desktop behaviour. The original fresh installs provide the installer evidence. Candidate ISO SHA-256: `7eb22d176d0b804de4a707aba6f5bbfb69748810f1eac3f658f1de5fd654ff5d`.

Two local follow-up commits address the desktop findings outside the installer branch. `e77b09b5a` limits the layout hint OCR to the panel's output. `d6d2dda9d` lets Hyprland choose the focused output when an overlay opens. In a disposable Hyprland session with stale Quickshell focus, the original component opened on the primary display. The fixed component opened on the focused 1.5× output, retained typed text when that output was removed and reopened on a new focused output. The probe used the production component with a minimal text field. All 42 overlay assertions passed. In a host run of the 441-file shell suite, seven of eight failing files also failed on the pre-overlay baseline. The provider reauthentication fixture passed on its isolated baseline run. Checks in 44 test files were skipped.

Rune applied both follow-ups unchanged to the installed `89ea3e2cb` RC71L candidate. The real menu passed both attempts, including first opens on successive 1920×3200 temporary outputs and recovery to the 1280×800 primary with its search text still present. The display-panel test initially stopped at an IPC peer-close before OCR. After one guest shell restart, it read both layout hints from the panel's output and passed. This covers virtual displays. The Ally's physical dock remains a separate check.

Local review branch `draft/rc71l-first-login-retry` at `c8c861626` builds on Quattro `419a5a709` and contains the original draft plus the offline retry fix. For the next paddle and RGB test, the official generic x86_64 `linux-cachyos-deckify` 7.3.3-1 package has been downloaded off-device. Its SHA-256 and signature match the vendor metadata and documented fingerprint. The archive includes the kernel and matching `hid-asus-ally` and `hid-asus` modules. A side-by-side boot can use the existing Limine kernel order, which puts `linux-omarchy` first. The Ally uses TPM2 auto-unlock on an encrypted system volume, so have its passphrase and a physical keyboard available before selecting a different kernel. The supported driver sends ring brightness and animation power-state commands during probe. A trial boot can change the controller's lighting settings even from USB. Check distinct paddle events and the joystick-ring LED interface before testing any new control profile. ## Order of work

1. **Verify the alpha on the physical unit.** Capture package versions and a rollback point, then test the full mode round trip, stick pointer, short/long power press and wake. Capture paddles while the unit and physical operator are available. Approve the power-backend handoff separately before testing writes. Keep a failed check open with its log and the exact build.
2. **Make the everyday controls complete.** Verify and fix TDP on repeated plug/unplug, desktop input after resume, keyboard focus and secure recovery. Then tackle the three hardware-dependent gaps with dedicated tests: RGB/paddles, external display/VRR, and speaker tuning. Keep backend and OSK changes independently reviewable.
3. **Run the installer work in parallel.** Use the [ISO builder](https://github.com/omacom/omarchy-iso/blob/quattro/README.md) with local Omarchy and package sources. Run the clean ISO install test without a reused base, then capture the physical RC71L first-login flow and a laptop control. Keep the draft focused on detection, laptop setup isolation and optional setup. Submit later pieces independently once their hardware results are recorded.
