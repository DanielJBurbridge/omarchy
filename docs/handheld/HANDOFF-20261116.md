## Handheld package versions

`omarchy update` on the Ally replaced our `omarchy-dev` and `omarchy-settings-dev` with upstream `4.0.0.r7967.g3b36b9e`. `vercmp` ranks a numeric segment above an alphabetic one, so `4.0.0…` beat `dev.202611170222.e742281c` and the swap looked like an upgrade. sddm then sat in a relogin loop.

`omarchy dev pkg-test` now sets:

`<base>.<commit UTC yyyymmddHHMM>.r<count>.handheld.<sha8>[.dirty]`

`<base>` is the checkout `version` file with a trailing `.alpha` removed, so `4.0.0.alpha` publishes `4.0.0`, the same base upstream `omarchy-dev` uses. The stamp is the committer time in UTC. `r<count>` is the total commit count, as in the omarchy-dev PKGBUILD. A dirty tree appends `.dirty`. Example: `4.0.0.202611170222.r8072.handheld.e742281c`.

The stamp sits where upstream puts the letter `r`. A number beats that letter, so the build stays above `4.0.0.r7967.g3b36b9e` and above a much higher `4.0.0.rN` (checked through `r999999`). Two builds sort by the stamp, including when a rebase lowers the commit count. The same string sorts above `dev.<date>.<sha>` and `dev.<sha>`, so the next deploy upgrades an Ally still on those packages.

Putting `r<count>` first does not. This fork is only about a hundred commits ahead of upstream `r7967`, and `vercmp` says `4.0.0.r8072.handheld…` is older than `4.0.0.r8200.gabcdef0`. An epoch would also stay above upstream, and it would stay above `4.0.1` and `9.0.0` too.

To go back while upstream is still `4.0.0.r*`, install that package with `sudo pacman -U` (or the saved copy under `~/omarchy-handheld-pkgs/<sha>/`). `omarchy update` will not do it. When upstream's base moves to `4.0.1` or later, `omarchy update` takes it. There is no epoch to clear. Morning-list item 7 is that explicit downgrade, for when the handheld changes are already in the repo build you are switching to. That `4.0.1` swap brings the sddm relogin loop back; [L221](alpha-followups.md) is the open follow-up, a gaming-session hook that turns handheld autologin off when the new pkgver has no `.handheld`.

This is Arch's VCS pkgver (`base.r<count>.g<sha>`, and the omarchy-pkgs note that the r-number is the whole history) plus pacman's vercmp rule that a numeric segment is newer than an alphabetic one. That is the same idea as a CachyOS `pkgrel` of `1.1`: newer than the current Arch package, and older than the next real upstream version. Epoch is the last resort in the Arch PKGBUILD guidelines, and it blocks that next version.
