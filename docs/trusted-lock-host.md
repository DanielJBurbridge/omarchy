# Trusted lock host (K07)

This is an integrated source implementation for serial rollout, not installed or physically verified Ally support. The recovery baseline is [the source recovery handoff](rog-ally-source-handoff-20261112.md); the subsequent presentation change is [the authentication UI handoff](rog-ally-auth-ui-handoff-20261112.md). The corrected SDDM/read-only producer stage remains independently releasable. The host is explicitly opt-in; with it off, the existing desktop shell remains the lock owner. No boot, encryption, PAM policy, logind policy or autologin setting changes.

## Security boundary and import closure

`shell/lock-host.qml` is a separate Quickshell configuration, outside `PluginRegistry`. This deliberately makes an exception to the single long-running desktop shell convention: a process boundary is needed because Qt Virtual Keyboard exposes its focused input QObject through `InputContext` to any importer in that process. Masking, private QML parents and detached authentication objects cannot hide the field from a process-wide caller-selected input context. A pure-QML private keyboard also cannot generally fix a caller's `QT_IM_MODULES=qtvirtualkeyboard` or provide full compositor XKB translation.

The fixed entry imports only the trusted lock service. Its active QML closure is `Service`, `LockView`, `LockStateSocket`, `LockControlSocket`, `FingerprintModel.js`, the fixed `Commons` palette/style/i18n/utility components, `Ui` background/border/button components, and `lock-host/Keyboard.qml`, plus the fixed packaged `QtQuick.VirtualKeyboard.Styles.Omarchy` module. Those load data such as theme colours, translations and background media; there is no desktop plugin registry, user QML loader, plugin facade, eval endpoint or application launcher API. The desktop preview is a fixed lazy source and is disabled in the trusted host. Qt's packaged keyboard layouts and native modules remain trusted dependencies; no upstream keyboard implementation is copied. Omarchy supplies only a fixed `KeyboardStyle` and visual controls/data in `/usr/lib/qt6/qml/QtQuick/VirtualKeyboard/Styles/Omarchy/`. SDDM and the lock host use this same module in their separate processes. The lock wrapper binds the existing Commons palette/typography to its data singleton; SDDM uses the existing `omarchy-plymouth-set` colour substitution and artwork pipeline. The singleton exposes only colours, dimensions and font data, with no authentication service or focused input object. Neither launcher gains a custom import path or accepts a caller-selected style. The source fixture alone adds the module source directory to Qt's import path.

The protected Bash entrypoints suppress `BASH_ENV` and exported functions before running isolated `/usr/bin/python3 -I`. The user unit removes native/interpreter injection variables before its first executable. Before exec, the launcher removes caller Qt/QML/JS/Quickshell and dynamic-loader overrides, including arbitrary keyboard layout/style and generic plugin paths, and sets only the trusted keyboard/backend settings. It uses the system Quickshell executable and Basic controls. The host uses `QT_IM_MODULE=qtvirtualkeyboard`, `QT_IM_MODULES=qtvirtualkeyboard`, `QT_VIRTUALKEYBOARD_DESKTOP_DISABLE=1` and Wayland. The desktop shell and applications launched from it retain the caller's exact IME values, including unset versus empty; Fcitx is not globally replaced.

This isolates authentication QObjects from unrelated desktop QML. It does not make third-party QML a sandbox against arbitrary same-UID native code or a compromised session account. Keep trusted installed runtime code and package dependencies under the normal package trust model. Never load a third-party component into the host to add a keyboard or theme.

## Ownership, supervision and readiness

`omarchy-lock-host.service` runs independently of the plugin-bearing desktop shell and is tied to `graphical-session.target`. A desktop restart kills only configurations ending in `/shell/shell.qml`; the trusted host has the distinct `/shell/lock-host.qml` identity. Restart preflight explicitly validates the external owner before permitting that restart while locked. An invalid/missing host with a compositor lock refuses desktop restart; it never kills the lock host or starts a competing local owner. Restart probes the compositor once and handles all three outcomes before any kill: proven unlocked follows normal restart, proven locked follows owner/recovery policy, and unknown/failed/unexpected results refuse without killing any client.

`omarchy-setup-lock-host enable|disable` stages the next graphical session only. It first requires both the canonical owner and compositor helper to prove unlocked. It refuses custom/replacement units and never uses `--now`, stops an owner, edits user unit files or restarts a shell. At graphical startup the first launcher atomically latches `host` or `shell` in `$XDG_RUNTIME_DIR/omarchy-lock-mode-$HYPRLAND_INSTANCE_SIGNATURE`. Both launchers read that immutable selection. Changing the future preference then restarting the main shell cannot promote or demote this session's owner. Staging disable also leaves the current host's automatic crash recovery available. `setup status`, canonical status and readiness queries never initialise the selection or start the service.

The host and generic owner take the same nonblocking kernel lease; the main broker has a separate lease. The host selection makes the main shell create only `Broker.qml`, with no PAM context, password field or `WlSessionLock`. There is no fallback owner if the opted-in host fails. Role records contain protocol, UID-checked process identity, process start time, session signature and canonical source root. A single bounded systemd query validates the exact packaged `FragmentPath`, empty `DropInPaths` and `MainPID`. The same manifest check runs during staging, host launch, peer acceptance and stranded recovery, so a later replacement unit or supervision-changing drop-in is rejected. Clients also check native `SO_PEERCRED`, executable and exact configuration argument. A role file or held lease alone never proves a compositor-secure lock.

Readiness means password PAM configuration is present and the initial stranded-lock check resolved; systemd `active` is not readiness. Secure means the actual `WlSessionLock.secure` state. The existing output stabilisation, orphan-lock recovery, password/fingerprint ownership and retry behaviour remain in the same lock service. If startup exhausts its 20 bounded orphan-check ticks, an explicit lock request can start a fresh bounded check. The client sends that request even while unready; the server retains only lock intent and does not extend a check already running. Unknown/competing-locker results cannot acquire a lock or report secure. A proof must also terminate normally: the installed Process signal carries `QProcess::ExitStatus` (`NormalExit=0`, `CrashExit=1`); a signal crash with numeric exit code 1 is not an unlocked proof. Once proofs resolve, the pending explicit request can begin locking. A status query never re-arms the budget. An immediate unready acknowledgement still fails the client rather than claiming success. For stranded recovery, only a matching live broker role is exempt from the conservative competing-locker check. A stale/dead role, unknown Quickshell process or another locker stays undetermined. The host must have its matching actual unit identity before attempting orphan reacquisition.

No new idle polling daemon is added. The broker uses socket events and a ready-file watch to refresh peer-checked scalar state. Existing bounded lock acquisition and recovery retries remain. Process death closes subscriber sockets; restart creates fresh snapshots.

## API contract

The canonical interface stays `omarchy-shell lock lock|isLocked|status`. Both direct and broker `isLocked` report true unless readiness is strictly true and actual locked is strictly false. When this session selected the host, the CLI goes directly to the independently validated host, including while the main broker is absent or restarting. Other methods and extra arguments are rejected. Status does not start it. Lock calls require the current `HYPRLAND_INSTANCE_SIGNATURE` and `WAYLAND_DISPLAY`; stripped TTY/SSH contexts are explicitly unsupported instead of guessed. For a host session, supplied values must match the live owner role/process environment. Both owner modes require the Wayland and signature-specific Hyprland IPC sockets to identify the same live compositor. Native peer UID, exact system compositor executable and equal compositor PID are checked at those endpoints. Missing/stale/mismatched values fail before any main-broker fallback. No newest-display or environment-only resolution is used for lock requests. Non-lock IPC retains its existing display recovery. Generic lock IPC still uses the main owner after compositor-context validation; that context proof does not require a live generic owner, preserving orphan-lock recovery. A locked desktop restart refuses an unsupported context before killing anything, rather than treating a failed query as evidence of owner death. A missing, invalid or unready host cannot report an unlocked usable owner. `isLocked` reports true for unready state; transport/identity failures return nonzero.

The private control endpoint is `$XDG_RUNTIME_DIR/omarchy-lock-control-$HYPRLAND_INSTANCE_SIGNATURE.sock`. It sends an initial scalar status snapshot; the only accepted requests are exact JSON lines `{"method":"lock"}` and `{"method":"status"}`. It has no password, unlock, submit, focus-object, preview, eval or arbitrary command request. Client output is whitelisted to protocol `1`, owner `trusted-host`, and strict boolean `ready`, `locked`, `requested`, `secure`. The broker treats socket traffic only as an event and obtains state through the peer-checked client. It fails closed on loss.

The actual owner publishes the unchanged INPUT endpoint `$XDG_RUNTIME_DIR/omarchy-lock-$HYPRLAND_INSTANCE_SIGNATURE.sock`, initial/changed newline JSON `{"locked":<strict bool>}`. Any inbound byte disconnects the subscriber; EOF invalidates saved state. Lock-requested, compositor-locked and secure transitions all re-read actual state. In host mode, unready is also reported as true/unknown; readiness produces a true-to-actual-state edge, so an early false snapshot cannot strand INPUT after canonical startup failure. Generic owner semantics stay unchanged. A true boolean never proves compositor-secure. INPUT must keep its canonical/compositor action guards and reconnect-on-recreation behaviour. Because canonical CLI status remains available directly through the host during main-shell restart, an unchanged boolean feed does not depend on a broker-return edge to recover.

`omarchy-system-sleep-lock` requires ready plus compositor-secure for the trusted owner. `omarchy-system-lock` propagates that failure when opted in. RELIABILITY's proactive suspend route must check that exit status before issuing sleep. This increment preserves the existing logind delay inhibitor: an external sleep request already issued to logind cannot be vetoed after that delay expires. It introduces neither a block inhibitor nor new sleep-request routing.

## Keyboard behaviour and layout limits

The keyboard is embedded only in the active secure surface, created on request, with a visible supported-Qt-layout chooser. Passwords mask immediately; the existing private submit/PAM path handles visible Unlock and Return. Cancel/Escape clears the entry and keyboard without unlocking. In-flight password checks reject duplicate submissions and disable cancellation; failure clears and refocuses for retry. Existing physical keyboard and fingerprint paths remain available.

Physical keys use the compositor keymap. Touch uses the chosen packaged Qt keyboard layout, including its Shift, symbols and alternatives. The layout chooser shows the actual locale. This does not claim arbitrary Hyprland XKB variants or Compose equivalence. Before target acceptance, record Daniel's actual layout/Compose requirements and any gap; do not change the compositor keymap to hide one.

## Reviewed package/install manifest

The PKGBUILDs live in the separate `omarchy-pkgs` repository. The [release recipe patch](../packaging/rog-ally-release/omarchy-pkgs.patch) adds the fixed user unit and explicit Python/Qt dependencies to the pinned recipes identified in the release handoff. Integration must build matching runtime/settings releases; dev link alone does not install the fixed user unit. This pairing is required even with trusted-host opt-in off: the generic runtime launcher, canonical lock and restart commands depend on the matching settings-owned `default/lock-host/control.py` helper. Do not publish or roll back only one package side. Generic mode does not activate the trusted-host unit. Required dependencies are the existing Quickshell/Python/PAM stack and `qt6-virtualkeyboard` matching the installed Qt ABI (source checks used Qt 6.12.0 and `qt6-virtualkeyboard` 6.12.0-1).

| `default/lock-host/control.py` | Matching settings-package helper under `$OMARCHY_PATH/default/lock-host/control.py`, mode 0644 |

| `shell/plugins/lock/{Service,LockView,LockPreview,LockStateSocket,LockControlSocket,Broker}.qml` and existing trusted Commons/Ui imports | Matching runtime shell sources under `$OMARCHY_PATH/shell/`; never install a partial owner migration |
| `bin/omarchy-launch-shell`, `omarchy-shell`, `omarchy-restart-shell`, `omarchy-system-lock`, `omarchy-system-sleep-lock` | Matching runtime broker/lifecycle entrypoints |

Only the rollout owner installs or activates this after independent source review. Record matching package versions/archive paths, checksums, package file ownership and existing user-unit overrides; keep physical keyboard/TTY recovery. Install the reviewed dependency/runtime/settings transaction and reload the user manager's unit definitions without starting the unit. Verify `FragmentPath` and no overriding drop-ins; the helper refuses replacement fragments and custom drop-ins. From a known unlocked desktop, load the matching main shell once with its normal restart helper so the new launcher latches this session's owner selection; a missing selection or invalid compositor context must not be treated as unlocked. Then stage `omarchy-setup-lock-host enable`, save work and deliberately end the graphical session. At next login inspect the latched owner, unit `MainPID`, role identity, readiness and actual lock security before touch-unlock acceptance. Do not stop an active lock owner to change modes or test recovery.

Rollback: from a known unlocked session run `omarchy-setup-lock-host disable`; the current host stays alive until planned logout. End that graphical session, then reinstall the saved matching runtime/settings releases before the next session if reverting source. Do not revert to an in-shell owner or remove the host package in the middle of a host-owned session. If the host is unready/orphaned, use physical keyboard/TTY recovery and a planned graphical-session boundary; do not bypass PAM or clear encryption. Retain the Qt dependency while installed/active SDDM still needs it.

## Verification and pending acceptance

Focused tests live in `lock-state-test.sh`/`trusted-lock-host-test.py`, `launch-shell-test.sh`, `restart-shell-test.sh`, `sleep-lock-test.sh` and `system-lock-test.sh`. The native private fixture uses real Qt keyboard input, real AF_UNIX credentials and temporary `pam_deny`/`pam_permit` policies with dummy text. It exercises non-US layout, native Shift label state, masking, submit/Return/cancel/failure/retry, forbidden requests, process isolation under a dangerous caller IME override, main broker restart, stream EOF and fresh host snapshots. Direct fixture clients substitute the combined unit-identity provider with the fixture PID; actual manifest parsing and override guards are tested separately using substituted systemd output. The fixture is not an installed systemd unit and the main broker correctly stays fail-closed against the real provider. No real user password or compositor lock is acquired. Ownership tests cover immutable session choice, staging changes, kernel lease collision, identity rejection and conservative competing-locker handling. The bounded-recovery fixture runs the actual service/control/timer wiring with an accelerated 20-tick budget and a substituted conservative/unlocked probe; it acquires no Wayland lock. Unit override tests substitute systemd output to exercise the production parser and launch/peer/recovery predicates. A separate native exec fixture proves that the shared owner lease survives a real Quickshell exec, rejects a second launcher and releases on process exit. A lease/mock is not evidence of actual compositor security.

Actual systemd/Wayland acceptance remains required: sole owner across login/logout, secure acquisition before proactive sleep, active lock survival across desktop restart, compositor restart/orphan reacquisition, actual competing locker refusal, ready-feed restart and INPUT recovery, touch geometry/focus on native/scaled/external outputs, target layout/modifier/symbol/Compose needs, PAM/fingerprint success/failure, and suspend/resume. Capture dummy-only screenshots outside Git. Offscreen source checks do not prove physical lock security. The session-context positive path is covered with substituted owner/compositor identity providers; an actual systemd/Wayland positive context still requires rollout acceptance. SDDM and early-boot encryption retain their separate acceptance boundaries in [rog-ally-authentication.md](rog-ally-authentication.md).
