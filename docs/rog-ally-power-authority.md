# Restricted power authority: session delegation decision

**Decision: no production registrar or grant is authorised by the current evidence.** The managed SESSION supervisor is a plausible place for a future registrar, but its PID has not been bound to the authenticated target logind session. The ordinary desktop entry bypasses it. Keep stock Manager **NO-INSTALL**, the setup hold and `NO_AUTO_START` intact. This increment supplies a source-grounded candidate protocol and private-bus denial proof; it adds no production daemon, hook, policy, grant issuer or hardware setter.

The [remediation proposal](rog-ally-manager-remediation.md) and all-three-PPT snapshot semantics remain prerequisites. [authority-evidence.json](../plans/rog-ally-manager/authority-evidence.json) pins the source comparisons and local reference files. It records uncertainty rather than turning process ancestry into authority.

## What the real source establishes

The supervisor and three relevant `.desktop` entries are identical in SESSION `c52affb7bd94aca48f4a1a218596d15716012a0f`, correction `63b49c8fec2c540d5fca74610596c91075892313`, frozen `47e0e976f47c86edf9962d0debde9b571fadc385` and next-stage `78e8e7eda6b107d2834f39ecc7defe574060d09c`:

- Optional `omarchy-handheld.desktop` and `omarchy-gamescope.desktop` execute `omarchy-session-start`. That Bash process invokes UWSM as a foreground child, invokes Gamescope through a child `systemd-run --user --scope`, waits, and loops between desktop and gaming. It does not exec itself into either child or explicitly move its own cgroup. This supports a possible surviving registrar location; it is not an observed logind mapping.
- Normal `default/wayland-sessions/omarchy.desktop` directly executes UWSM and bypasses the supervisor. It has **no registrar coverage** under this proposal. Do not silently enrol ordinary desktop sessions or change their login entry.
- Installed Sigil UWSM `0.27.1-1` starts `wayland-session-bindpid@<its-own-PID>.service`, then execs `systemd-cat`/`signal-handler.sh`, whose child waits for a user service. The Bash supervisor remains waiting outside that compositor service. `systemd-run --user --scope` also moves scoped work under the user manager; parent/environment inheritance does not establish the child's original logind session or DRM/libseat access. The c52 scope comment is not authority evidence.
- Upstream SDDM `v0.21.0` (`63780fcd79f1dbf81a30eef48c28c699ab15aded`) authenticates, opens the PAM session and starts the configured Wayland SessionCommand. `PamBackend::openSession` calls `pam_open_session` before `Backend::openSession` starts `UserSession`. Sigil's Wayland wrapper finally execs the selected command, and its PAM stack includes **optional** `pam_systemd`. This establishes expected ancestry, not successful target registration or the installed target's exact patched behaviour. [SDDM helper](https://github.com/sddm/sddm/blob/63780fcd79f1dbf81a30eef48c28c699ab15aded/src/helper/HelperApp.cpp), [PAM backend](https://github.com/sddm/sddm/blob/63780fcd79f1dbf81a30eef48c28c699ab15aded/src/helper/backend/PamBackend.cpp), [session child](https://github.com/sddm/sddm/blob/63780fcd79f1dbf81a30eef48c28c699ab15aded/src/helper/UserSession.cpp).

`XDG_SESSION_ID`, `OMARCHY_HANDHELD_SESSION`, runtime filenames/flock and the user-manager logout worker are routing/orchestration data, not authority. A script filename, parent chain, desktop-entry selection or successful GetSessionByPID association is also not proof of trusted script contents or permission to perform arbitrary root actions.

No supervisor/registrar PID-to-logind mapping, session properties or lifetime across transitions/resume has been observed on the Ally. The existing SESSION orchestration fixtures stub systemd/logind boundaries and cannot supply that proof. Further target observation belongs to the sole rollout owner after staged installation and deliberate managed login; this task requests no probe or credentials.

## Candidate root-owned protocol, not an implemented API

Separate a narrow authority object from a restricted power object. All names below describe a review contract, not installed interfaces. The root side must derive message credentials itself; a supplied name can only locate a pending peer and cannot prove ownership.

| Stage | Candidate request | Required root checks before authority state changes |
| --- | --- | --- |
| Identify | `GetCapabilityIdentity1()` | Read-only protocol/build/boot/mode identity. No auto-start or authority. Restricted mode must advertise non-power duties absent and complete profile/PPT API version; a version string alone is insufficient. |
| Prepare proxy | `PrepareProxy1(challenge: ay[32])` from the actual proxy | Obtain its **unique system-bus sender**, broker UID/PID and a race-safe process reference. Create only a short-lived pending connection record after valid credentials, not a power grant. Bind challenge, sender and process lifetime; do not accept an arbitrary PID or a well-known name as identity. |
| Request enrolment | `RequestGrant1(pending_proxy_id: ay[16])` from the in-session registrar | Resolve registrar credentials and genuine logind session/seat; re-resolve the prepared proxy's credentials, require matching UID and its live pending challenge. Request narrowly scoped Polkit consent using the **actual registrar system-bus name** as subject. The pending ID only locates a root-held record; its secrecy is not authorisation. |
| Complete enrolment | Root completes the pending authorisation, then proxy confirms its challenge on its original connection | Recheck both peers, session properties/seat, build/boot and pending expiry **after** the asynchronous Polkit result. No grant if either connection disappeared, changed, or became ambiguous during prompting. Issue a root-held grant for this exact proxy connection and anchor. |
| Renew/rebind | `RenewGrant1` from the retained registrar; for replacement proxy first repeat PrepareProxy | Revalidate the original anchor and actual sender credentials, obtain fresh noninteractive Polkit approval, and repeat the two-party binding. Revoke the old proxy grant first. A restarted proxy cannot renew itself using a UID, environment SID, previous token or reacquired well-known name. |

The pending proxy/registrar rendezvous itself still needs an agreed SESSION transport: an explicitly inherited/private channel or an explicit user-confirmed pairing flow. A shared user-bus name, user-writable runtime file or arbitrary same-UID request is not a substitute for that binding. No such rendezvous code exists in current SESSION. The protocol does not attest proxy/script executable contents; it delegates only the fixed root-enforced profile/PPT action set to a verified connection after explicit consent. Do not label a matching `/proc/PID/exe` path as code attestation, particularly for interpreters or preloadable programs.

Required session evidence is a real, race-safe mapping of the registrar process to a logind object. Read `Id`, `User`, `Service`, `Class`, `Type`, `Remote`, `Seat`, `Active`, `State`, `LockedHint` and `Scope`, and the seat's `ActiveSession`. Require the expected UID, SDDM service, graphical user class/type, local seat, active/unlocked state, matching active session and a live original session scope. Restrict the first variant to one unambiguous graphical login/registrar/proxy for the UID/seat; multiple sessions, changing objects or ambiguous detached-proxy association mean denial. Never select “the active session for this UID” to fill a missing process mapping.

Broker UID/PID must refer to the actual message sender, using `GetConnectionCredentials`/equivalent trusted transport credentials. Production needs a trustworthy process-lifetime reference before session resolution: prefer non-augmented, broker-supplied pidfd credentials and `sd_pidfd_get_session`, cross-checked with logind. A later `pidfd_open` on an unchecked numeric PID does not retroactively prove it is the broker's original process. systemd's `sd_bus_creds_get_augmented_mask` documentation explicitly warns that augmented credentials are racy and unsuitable for authorisation; do not treat proc-derived session metadata as broker-attested credentials. If an atomic/race-safe binding cannot be established on the actual bus/library stack, deny and resolve that implementation dependency first. The private proof below checks numeric credentials only for denials; it grants nothing and establishes no pidfd acceptance path.

The trusted login1 and Polkit endpoints must themselves resolve to the expected root-owned system services, not just well-known names. Pin/check their actual unique owners and credentials and fail closed on owner loss/replacement; root ownership is necessary, not proof that an arbitrary root process or private test service is the target authority. No live authority query is part of this increment.

## Grant state machine and lifetime

The candidate state sequence is `Absent -> PendingPeer -> PendingConsent -> Bound`, with terminal/recovery states `Expired`, `Revoked` and `NeedsInteraction`. Only a completed, revalidated Bound state can admit a power transaction. Failed bootstrap must not touch power preferences, recovery journals, hardware or PPD ownership. Pending/audit bookkeeping is not an authority grant. No successful issuance path is implemented by this task.

| Event | Required transition and action |
| --- | --- |
| Registrar/proxy/session unknown; second ambiguous login/registrar; absent trusted login1/Polkit; credential mismatch | Deny; discard pending state. No UID/env/name fallback. |
| Explicit user enrolment, after a graphical Polkit agent is available | May enter PendingConsent. Use a dedicated fixed-action policy, initially active-local `auth_admin_keep`; inactive/remote defaults deny. No arbitrary subject/details from clients. No authority before the result and post-result checks. |
| Valid completion | Proposed grant TTL maximum 60 seconds on a suspend-aware monotonic clock, also bounded by the root pending/consent lifetime. Bind registrar/proxy unique senders and stable credentials, UID, exact logind object and generation, seat, backend build, boot and permitted operations. Tokens are opaque locators, not bearer authority. |
| Expiry | Reject new operations immediately. A one-shot deadline or comparison at the request boundary is enough; no periodic keepalive/renewal service. Expired grants cannot renew themselves. |
| Renewal while anchor remains valid | Trigger only on an explicit operation or a relevant native event. Registrar must obtain fresh **noninteractive** Polkit approval; cached-admin interaction is usable only if Polkit still authorises this actual subject/action. Never extend consent merely because an earlier decision was cached by the application. |
| Cache expired/challenge required | NeedsInteraction. Only an explicit user action may initiate a new interactive request. Background AC/DC/resume events must fail visibly without launching an authentication prompt or treating the cache as permanent session consent. |
| Proxy crash/name loss | Revoke the old grant and pending records via NameOwnerChanged plus process lifetime. Rebinding requires a new real proxy connection, pending challenge and surviving registrar authorisation. Reusing the service name or old token cannot rebind. |
| Registrar exit, inactive/locked session, logout, seat change, login1/Polkit owner change, boot/backend-build change | Revoke, invalidate captures/new requests, and require a fresh bootstrap/consent as appropriate. Existing root transaction cleanup remains server-owned; revocation must not strand a partially written tuple by killing cleanup. |
| PrepareForSleep(true)/resume | Suspend admission and invalidate grants/observations. On resume re-resolve the original anchor, active/unlocked session and authority, and recapture source/capabilities before any transaction. A resume signal alone never recreates a grant. |

This deliberately conservative cache/TTL policy leaves a concrete UX gap: automatic AC/DC/resume restoration cannot be promised after authorisation expires or while locked. A policy for useful unattended bounded restoration needs explicit review; do not solve it with all-yes Polkit, indefinite cached admin consent or an active-UID inference. No production grant is cleared until the interaction/lifetime policy and SESSION rendezvous are agreed and tested.

## Restricted power surface and takeover dependency

The first server entry point is limited to capability identity, authorised complete `CaptureProfilePpt1`, bounded/idempotent `ApplySustained1`, exact `RestoreProfilePpt1` and authorised `GetTransaction1`, with completion signals. Requests reference root-held grants/snapshots and expected epochs; root checks connection binding, live authority, actual device/source/caps and the complete three-field footprint on every operation. Missing/expired/revoked grants must be denied before transaction/journal/hardware mutation. Transaction status is not public merely because someone guesses an ID. The typed snapshot/partial-write/timeout/source-transition contract in the remediation proposal is unchanged.

No network, input, login/session selection, BIOS, storage, scheduler, generic command/sysfs or legacy RootManager interface is registered. Initial scope retains **no Steam QAM legacy adapter** until its per-request origin/deputy boundary is reviewed: a user-wide session proxy can otherwise forward calls from unrelated sessions under its own grant. If retained later, adapters must enter the same root-authorised engine, carry a proven permitted invocation path and never bypass bounds, grant lifetime or capture completeness. Existing QAM flags and same-UID bus access prove neither.

A future setup must require an observed valid anchor, successful restricted capability/authority handshake and a complete read-only baseline **before** stopping/masking PPD. Fail before takeover if managed-session entry, registrar, rendezvous, Polkit agent/approval, process binding, complete capture or current hardware policy is unavailable. Under current evidence every real enrolment remains denied. Existing ordinary desktop/laptop PPD behaviour is unchanged.

Safe alternatives are to keep generic PPD and unavailable restricted controls, or later explicitly use a newly reviewed in-session client/registrar whose actual logind mapping is proved. Expanding the ordinary SDDM entry to retain such a client would be a separate SESSION/AUTH change. Moving a process after the fact, borrowing another process's SID, weakening PAM or relying on a parent/environment variable is not an alternative authority source. There is no new production wrapper or service here.

## Private-bus proof and exact limits

[authority-denial.py](../plans/rog-ally-manager/authority-denial.py) runs as an ordinary user with an actual private dbus-daemon and two distinct child processes. Both session/system bus addresses and every connection are explicitly private. It invokes real broker `GetConnectionCredentials`, compares received PID/UID to the actual child processes, rejects a well-known name as proxy identity, rejects absent login1 and a trusted-looking login1 name owned by an unprivileged peer, and observes real NameOwnerChanged/name disappearance. Bogus session environment variables never become credentials. Unknown grants cannot reach the capture/transaction/status handlers; login/network/BIOS/storage/input methods are absent from the fixture interface.

The fixture contains no grant issuer/store, positive fake logind/Polkit response or hardware writer. It demonstrates real credential transport and negative trust/lifetime gates, **not** successful grant issuance, a complete lifecycle validator or active/inactive/expiry/resume acceptance. Its protected method signatures are reduced to an opaque token to exercise denial and are **not** the production wire ABI. Missing authority is tested against the real private broker, not a stub that declares its own fake session valid. No privileged policies or services are installed.

Run it explicitly with `python3 -B plans/rog-ally-manager/authority-denial.py` in a sandbox that permits private Unix sockets. It never connects to the live system/session bus, reads live logind sessions or probes the Ally. No full Manager/Rust build occurs. A passing fixture cannot clear the target evidence gate.

## Remaining target evidence and recommendation

The sole rollout owner's root-relayed firmware capture establishes exact `asus-armoury` SPL/SPPT/FPPT paths and current raw values **30/43/53**, already in performance mode on AC. Units were not attested, and there was no outside-performance capture, profile change, write/restore or safe burst-cap approval. This is useful current-profile readability evidence, unrelated to authenticated-session authority. Do not label those raw integers verified watts or claim complete pre-profile capture. The proposed watts-based API still requires an explicit verified units conversion/identity contract.

Required target evidence is still absent: real registrar sender credentials plus race-safe process identity; PID/pidfd-to-logind mapping and the listed session/seat/scope properties; continued original anchor lifetime through desktop/gaming transitions; inactivity, lock/logout, proxy restart and suspend/resume revocation/rebind behaviour; and the concrete consent/rendezvous/adapter boundary. Staged managed login remains blocked outside this source task. No additional probe is requested here.

Recommendation: retain denial and generic PPD now. Review this restricted surface/state machine, SESSION rendezvous and authorisation UX before any production registrar implementation. Then obtain the missing targeted session evidence through the existing rollout owner and implement isolated positive/hostile lifecycle tests. Complete PPT hardware execution, locked build/package/signature/manifest review and takeover remain separate later steps. There is no basis for a production grant, package activation or hardware-writing backend in this increment.
